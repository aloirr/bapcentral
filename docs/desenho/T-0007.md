## 1. Problema e fatos

**A gravação pela API está barrada.**
- `enviar` e `lido` gravam com `criarClienteDeRecados().commitar` (`scripts/coord-lib.mjs`), que usa os endpoints de escrita da API do GitHub (blobs, árvores, commits, refs).
- Na nuvem, o proxy da sessão responde ao primeiro POST com HTTP 403 e a mensagem `Write access to this GitHub API path is not permitted through this proxy`.
- Nada é publicado.

**A leitura pela API funciona**: `caixa`, `pendencias`, `ler` e `fio`.

**O `git push` ao `main` do repositório de recados funciona nesta sessão.** O histórico da T-0001 (commit `19cb290`) registra:
- a orientação do Alexandre, no R-20261120-091403-po;
- os commits `99a2f4f` e `66621f6` no `main` dos recados, empurrados por git à mão;
- hoje o `main` está em `2ca2544`.

Esse push não foi meu: ficou proibido nesta tarefa. Vale como prova de fato, com uma ressalva (R1).

**Falha nova (critério 7).** O `agoraLocal()` do `coord.mjs` usa o fuso da máquina, e o contêiner roda em UTC. Por isso os ids e o `criado_em` gravados na nuvem saem 4 h adiantados.

**O PC Windows do Alexandre** grava pela API (com o `gh auth token`). Isso tem de continuar igual.

## 3. Como funciona

```
coord enviar / lido
  ├─ leitura: API REST, igual a hoje (índice + cache por commit)
  ├─ gravação, conforme BAP_RECADOS_ESCRITA:
  │    api  → commitar pela API (igual a hoje)
  │    auto → (padrão) tenta a API; com o 403 do PROXY (nada publicado) passa ao git, com um aviso de 1 linha
  │    git  → direto ao git
  └─ git (repositório bare só do coord, em <cache>/git-aloirr-bapcentral-recados, fora de qualquer clone):
       ls-remote → fetch --depth=1 do topo do main
       hash-object + índice temporário + write-tree + commit-tree (pai = topo)  → um commit, atômico
       push SEM force; recusado por concorrência → busca de novo, remonta e tenta de novo (até 6 vezes, com espera)
       resposta perdida → confere o topo antes de dar erro ("confirmado na conferência")
     saída: "Recado R-... enviado para ... (GitHub ...@abc1234, por git push)"

Plano B (BAP_RECADOS_RAMO=claude/<sessão>): mesmo gravador no ramo da sessão;
  a Action integrar-recados.yml integra no main; o enviar espera o recado no main (BAP_RECADOS_ESPERA_S, padrão 120)
  e, se o prazo acabar, sai 3 ("gravado no ramo, ainda NÃO está no main. NÃO reenvie").
```

Por que um repositório bare no cache, e não o clone `/home/user/bapcentral-recados`:
- não mexe na árvore, no índice nem no HEAD de quem usa o clone à mão (o po e o gerente fizeram isso hoje);
- não depende de onde o clone fica nem do estado dele;
- `--depth=1` deixa tudo pequeno;
- a credencial é a do git da máquina (na nuvem, a do proxy). O coord nunca a vê.

## 4. Arquivos e funções que mudam

### `aloirr/bapcentral`: `scripts/coord-lib.mjs` (governança)

**Detecção do 403 do proxy**
- `ErroRecados` ganha `proxy` (o proxy da sessão barrou a gravação e nada foi publicado).
- `ehNegadoPeloProxy(r)` (nova, pura): verdadeira só com o 403 **e** o texto `not permitted through this proxy`. Um 403 do próprio GitHub (limite de uso, permissão) não conta.
- `criarClienteDeRecados`:
  - `json()` lança `{proxy:true}` antes do 403 genérico;
  - método novo `arquivoNoRamo(caminho, ramo)`, só leitura, usado no plano B.
- `enviarRecadoNoGitHub` e `marcarLidosNoGitHub`: com `e.proxy`, relançam na hora, sem conferência e sem gastar as 6 tentativas. O resto não muda.

**Funções novas**
- `modoDeEscrita(env)` → `api` | `git` | `auto`. Vem de `BAP_RECADOS_ESCRITA`; o padrão é `auto`.
- `ramoDeEscrita({env})`:
  - sem variável, `main`;
  - com `BAP_RECADOS_RAMO`, o valor dele;
  - nome com `..`, com `/` no início ou fora de `[A-Za-z0-9._/-]` dá `null`, e o erro é claro.
- `horaLocal(data, fuso='America/Manaus')` (pura): mesma função do `recados-lib.mjs` do formulário. Devolve `{iso: '...-04:00', compacto}`.
- `limparSaidaDoGit(t)`: tira `usuario:senha@` das URLs, tira linhas com token/authorization/password/senha e deixa no máximo 3 linhas.
- `gitSincrono({env})`:
  - `spawnSync('git')` sem shell, com `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C` e `windowsHide`;
  - sem o git no PATH, dá o erro "git não encontrado no PATH".
- `unirLinhas(...textos)` (pura): linhas sem repetir, na ordem (o `main` primeiro).
- `criarGravadorGit({git, url, ramo, pasta, principal, tentativas, esperar})` → `{ramo, publicar(montar)}`:
  - `montar(leitor)` é chamado de novo a cada tentativa, sobre a base nova. O `leitor` traz `ids`, `existe(c)` e `texto(c)`;
  - trava entre processos da mesma máquina (`bap-coord.lock`): a criação do bare fica dentro dela, a trava é abandonada depois de 120 s e a espera máxima é de 60 s;
  - recusa por concorrência nos **dois** formatos:
    - no cliente: `[rejected]`, `fetch first`, `non-fast-forward`;
    - no servidor: `cannot lock ref`, `incorrect old value`, `failed to update ref`.
    - O protótipo pegou o segundo formato numa corrida real; sem ele, um envio falhava;
  - push negado (403, "not permitted", "denied") → `ErroRecados{proxy:true}`, com a dica do plano B quando o alvo é o `main`;
  - `-S` só se `commit.gpgsign=true`, porque o `commit-tree` não lê essa configuração sozinho (conferido no git 2.43). Também `push.negotiate=false`;
  - identidade: a do git da máquina. Se não houver, usa `bap-coord`.
- `esperarNoMain({cliente, caminho, blob, prazoMs, passoMs})`: só no plano B.
- `enviarRecadoPorGit(...)` → `{id, commit:{oid, ramo}, integrado}`:
  - os ids vêm do `main` (API) e da base do git, então o mesmo segundo vira `-2`;
  - `--responde-a` é conferido nesse mesmo conjunto;
  - nunca sobrescreve: id que já existe dá erro;
  - com ramo = `main`, `integrado` sai `true` na hora.
- `marcarLidosPorGit(...)`: o arquivo recebe as linhas do `main`, depois as da base, depois as novas. Sem nada novo, não há commit.
- `gravadorGitDeRecados({env, ramo})`:
  - o bare fica em `pastaDoCacheDeRecados(env)/git-<repo>`;
  - a URL vem de `BAP_RECADOS_GIT_URL`; o padrão é `https://github.com/<repo>.git`, e os testes usam `file://`.

## 6. Garantias (critérios 2 a 5 e 7)

- **Atômico e sem sobrescrever:**
  - um commit por envio, com todos os destinos;
  - recusa de id que já existe no `main` ou na base;
  - push sem force.
- **"Enviado" só com a confirmação do GitHub:**
  - push aceito, ou topo conferido depois de uma resposta perdida;
  - erro → "NÃO enviado (nada foi gravado)", e nunca "enviado";
  - no plano B, só com o blob no `main`.
- **Concorrência (critério 3):**
  - mesma máquina: a trava;
  - processos ou sessões diferentes: a recusa do push, mais busca, remontagem e nova tentativa;
  - conferido no protótipo: 2 processos × 5 recados ao mesmo tempo, no `main` e num ramo, com 10 de 10 gravados e retentativas observadas;
  - PC pela API × nuvem pelo git: os dois dependem do *fast-forward* do mesmo `main`.
- **Lidos:** união explícita (main, depois a base, depois as novas). O `merge=union` do `.gitattributes` continua valendo para quem usa o clone à mão.
- **Token (critério 5):**
  - o modo git não lê nem passa o `BAP_RECADOS_TOKEN`;
  - a leitura pela API continua com o token só na memória ou no stdin;
  - erros do git passam por `limparSaidaDoGit`.
- **Fuso (critério 7):** `horaLocal` com `Intl` e `America/Manaus`. O protótipo rodou com `TZ=Asia/Tokyo` e gravou `-04:00`.
- **Windows:** `path.join`, sem `/tmp` fixo, `spawnSync` sem shell e `windowsHide`. Nenhuma dependência nova.
- **Critério 4:** com o diff aplicado, os 26 testes de `coord-recados` e os 77 de `coord-verificar` de hoje continuam verdes.

## 7. Riscos

- **R1 🟡 O proxy pode passar a barrar o push ao `main`.** Hoje passa. A regra pública da sessão fala em "ramo da sessão" [SUPOSIÇÃO: pode ser exceção do repositório anexado com permissão de push].
  - Mitigação: o erro "push ao main negado" já sugere o plano B.
  - A Action fica pronta no diff.
- **R2 🟢 Push no `main` sem a validação da Action.** O risco é o mesmo de hoje: o token "Contents: write" e o git à mão já gravam qualquer arquivo. O coord só escreve `recados/<destino>/<id>.md` e `lidos/<agente>.txt`, depois das regras do `regraDoRecadoNovo`.
- **R3 🟢 O texto do 403 mudar.** O `auto` deixa de detectar e volta ao "NÃO enviado" de hoje, sem gravar pela metade. A `BAP_RECADOS_ESCRITA=git` resolve.
- **R4 🟢 Git à mão e coord juntos.** O coord não toca no clone. Quem empurra à mão com o clone atrasado recebe a recusa (não é *fast-forward*) e faz `git pull --rebase`, e os lidos se juntam pelo `merge=union`. Recomendo que, com o coord no ar, o time **pare de gravar à mão** (P1).
- **R5 🟡 (plano B) Workflow vindo do ramo.**
  - No `push`, o GitHub roda o `.yml` do commit empurrado.
  - Mitigações: o script vem do `main`, e o coord não muda nada fora de `recados/` e `lidos/`.
- **R6 🟡 (plano B) A plataforma mexer no ramo da sessão** (há `CLAUDE_CODE_SYNC_SESSION_REFS` no ambiente) [SUPOSIÇÃO: não observado]. Também vale o custo de minutos de Actions, estimado em ≈ 2.000 min/mês com 80 gravações por dia útil.
- **R7 🟢 Autoria dos commits.** É a identidade do git da sessão. O remetente verdadeiro está no cabeçalho do recado e no id.
