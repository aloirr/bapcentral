## 3. Como funciona

```
coord enviar / lido
  ├─ leitura: API REST, igual a hoje (índice + cache por commit)
  ├─ gravação, conforme BAP_RECADOS_ESCRITA (não definida nos ambientes, D2 → auto):
  │    auto → (padrão) tenta a API; com o 403 do PROXY (nada publicado) passa ao git, com um aviso de 1 linha
  │    api  → commitar pela API (igual a hoje)
  │    git  → direto ao git
  └─ git (repositório bare só do coord, em <cache>/git-aloirr-bapcentral-recados, fora de qualquer clone):
       fetch --depth=1 do topo do main
       hash-object + índice temporário + write-tree + commit-tree (pai = topo)  → um commit, atômico
       push SEM force ao main
         recusado por concorrência → busca de novo, remonta e tenta de novo (até 6 vezes, com espera)
         outra falha (resposta perdida?) → busca o topo do main DE NOVO e confere o blob de cada arquivo:
           presente → "confirmado na conferência"; o main mudou sem ele → nova tentativa;
           nada mudou → "NÃO enviado (nada foi gravado)"; a conferência não respondeu → "NÃO foi confirmado; confira com ler"
     saída: "Recado R-... enviado para ... (GitHub ...@abc1234, por git push)"
```

Por que um repositório bare no cache, e não o clone `/home/user/bapcentral-recados`:
- não mexe na árvore, no índice nem no HEAD de quem usa o clone à mão (o po e o gerente fizeram isso hoje);
- não depende de onde o clone fica nem do estado dele;
- `--depth=1` deixa tudo pequeno;
- a credencial é a do git da máquina (na nuvem, a do proxy). O coord nunca a vê.

### `scripts/coord-lib.mjs` (governança)

**Detecção do 403 do proxy**
- `ErroRecados` ganha `proxy` (o proxy da sessão barrou a gravação pela API e nada foi publicado).
- `ehNegadoPeloProxy(r)` (nova, pura): verdadeira só com o 403 **e** o texto `not permitted through this proxy`. Um 403 do próprio GitHub (limite de uso, permissão) não conta.
- `criarClienteDeRecados`: `json()` lança `{proxy:true}` antes do 403 genérico.
- `enviarRecadoNoGitHub` e `marcarLidosNoGitHub`: com `e.proxy`, relançam na hora, sem conferência e sem gastar as 6 tentativas. O resto não muda.

**Funções novas**
- `modoDeEscrita(env)` → `api` | `git` | `auto`. Vem de `BAP_RECADOS_ESCRITA`; o padrão é `auto`. A variável existe no código para teste e para voltar atrás, mas não vai aos ambientes (D2).
- `horaLocal(data, fuso='America/Manaus')` (pura): mesma função do `recados-lib.mjs` do formulário. Devolve `{iso: '...-04:00', compacto}`.
- `limparSaidaDoGit(t)`: tira `usuario:senha@` das URLs, tira linhas com token/authorization/password/senha e deixa no máximo 3 linhas.
- `gitSincrono({env})`:
  - `spawnSync('git')` sem shell, com `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C` e `windowsHide`;
  - o filho recebe o ambiente **sem** o `BAP_RECADOS_TOKEN`. `GH_TOKEN` e `GITHUB_TOKEN` ficam, porque um helper de credencial do git da máquina (por exemplo, o do `gh`) pode depender deles; o coord não os lê no modo git nem os põe em argumento;
  - sem o git no PATH, dá o erro "git não encontrado no PATH".
- `criarGravadorGit({git, url, pasta, tentativas, esperar, velhaMs})` → `{ramo: 'main', publicar(montar)}`:
  - `montar(leitor)` é chamado de novo a cada tentativa, sobre a base nova. O `leitor` traz `ids`, `existe(c)`, `texto(c)` e `blob(c)`. O plano devolvido pode trazer `confirmado(leitor)` (os lidos usam: todos os ids novos presentes); o padrão é "todo arquivo com o blob enviado";
  - trava entre processos da mesma máquina (`bap-coord.lock`), com a criação do bare dentro dela. Quem segura a trava **renova o mtime antes de cada comando git**; como cada comando tem timeout de 120 s, a trava só é dada como abandonada depois de 180 s sem renovação (`velhaMs`), e não pelo tempo total do envio. A espera máxima de quem chega é de 60 s, com erro claro;
  - recusa por concorrência nos **dois** formatos, com nova tentativa:
    - no cliente: `[rejected]`, `fetch first`, `non-fast-forward`;
    - no servidor: `cannot lock ref`, `incorrect old value`, `failed to update ref`.
    - O protótipo pegou o segundo formato numa corrida real; sem ele, um envio falhava;
  - **qualquer outra falha do push → conferência igual à do modo API**: busca o topo do `main` de novo (`refs/bap/conferencia`) e confere o blob de cada arquivo nesse topo. Assim, um push de outro agente logo depois do nosso não engana: o recado continua lá, com o mesmo blob. Presente → `conferido:true`. O topo mudou sem ele → nova tentativa. Nada mudou → erro "nada foi gravado". A conferência não respondeu → erro `naoConfirmado`, e quem chama manda conferir com `ler` antes de reenviar (mesma frase do modo API);
  - push negado (403, "not permitted", "denied") e não conferido → erro "o git push ao main dos recados foi negado: ... Avise o Alexandre (desenho T-0007, plano B)";
  - `-S` só se `commit.gpgsign=true`, porque o `commit-tree` não lê essa configuração sozinho (conferido no git 2.43). Também `push.negotiate=false`;
  - identidade: a do git da máquina. Se não houver, `bap-coord <bap-coord@bap-coord.invalid>`: o domínio `.invalid` é reservado e não pode atribuir o commit a uma conta real.
- `enviarRecadoPorGit(...)` → `{id, commit:{oid}, tentativas, conferido?}`, **o mesmo formato** do `enviarRecadoNoGitHub` (a CLI lê `r.conferido` nos dois modos):
  - os ids vêm do `main` (API) e da base do git, então o mesmo segundo vira `-2`;
  - `--responde-a` é conferido nesse mesmo conjunto;
  - nunca sobrescreve: id que já existe dá erro.
- `marcarLidosPorGit({gravador, agente, ids})` → `{novos, commit?, conferido?}`, como o `marcarLidosNoGitHub`: sobre o texto de `lidos/<agente>.txt` no topo do `main`, **só acrescenta ao fim** os ids que faltam. As linhas que já estavam ficam como estão (nada aparado nem apagado). Sem nada novo, não há commit.
- `gravadorGitDeRecados({env})`:
  - o bare fica em `pastaDoCacheDeRecados(env)/git-<repo>`;
  - a URL vem de `BAP_RECADOS_GIT_URL`; o padrão é `https://github.com/<repo>.git`, e os testes usam `file://`.

## 6. Garantias (critérios 2 a 5 e 7)

- **Atômico e sem sobrescrever:**
  - um commit por envio, com todos os destinos;
  - recusa de id que já existe no `main` ou na base;
  - push sem force.
- **"Enviado" só com a confirmação do GitHub:**
  - push aceito; ou, depois de uma resposta perdida, o blob do recado conferido no topo do `main` buscado de novo, como o `enviarRecadoNoGitHub` faz com `cliente.arquivo(caminho)`. Um push de outro agente logo depois do nosso não faz a CLI dizer "NÃO enviado" com o recado já no `main`;
  - erro → "NÃO enviado (nada foi gravado)" só quando a conferência mostra que nada entrou; sem conferência possível → "NÃO foi confirmado", com a orientação de conferir com `ler` antes de reenviar. Nunca "enviado" sem confirmação.
- **Concorrência (critério 3):**
  - mesma máquina: a trava, renovada a cada comando git;
  - processos ou sessões diferentes: a recusa do push, mais busca, remontagem e nova tentativa;
  - conferido no protótipo: 3 processos (2 no mesmo cache) × 5 recados ao mesmo tempo, com 15 de 15 gravados e retentativas observadas;
  - PC pela API × nuvem pelo git: os dois dependem do *fast-forward* do mesmo `main`.
- **Lidos:** como na API, só acréscimo ao fim do texto do topo do `main`. O `merge=union` do `.gitattributes` continua valendo para quem usa o clone à mão.
- **Token (critério 5):**
  - o modo git não lê o `BAP_RECADOS_TOKEN` e o tira do ambiente do processo do git;
  - a leitura pela API continua com o token só na memória ou no stdin;
  - erros do git passam por `limparSaidaDoGit`.
- **Fuso (critério 7):** `horaLocal` com `Intl` e `America/Manaus`. O protótipo rodou com `TZ=Asia/Tokyo` e gravou `-04:00`.
- **Windows:** `path.join`, sem `/tmp` fixo, `spawnSync` sem shell e `windowsHide`. Nenhuma dependência nova.
- **Critério 4:** com o diff aplicado, os 26 testes de `coord-recados` e os 77 de `coord-verificar` de hoje continuam verdes (103 de 103 no scratchpad).

## 7. Riscos

- **R1 🟡 O proxy pode passar a barrar o push ao `main`.** Hoje passa. A regra pública da sessão fala em "ramo da sessão" [SUPOSIÇÃO: pode ser exceção do repositório anexado com permissão de push].
  - Mitigação: o erro diz "negado", nada é gravado e a mensagem manda avisar o Alexandre. O plano B está descrito na seção 11, com o que resolver antes de ativar.
- **R2 🟢 Push no `main` sem a validação da Action.** O risco é o mesmo de hoje: o token "Contents: write" e o git à mão já gravam qualquer arquivo. O coord só escreve `recados/<destino>/<id>.md` e `lidos/<agente>.txt`, depois das regras do `regraDoRecadoNovo`.
- **R3 🟢 O texto do 403 mudar.** O `auto` deixa de detectar e volta ao "NÃO enviado" de hoje, sem gravar pela metade. Aí cabe a `BAP_RECADOS_ESCRITA=git` nos ambientes, por decisão do Alexandre.
- **R4 🟢 Git à mão e coord juntos.** O coord não toca no clone. Quem empurra à mão com o clone atrasado recebe a recusa (não é *fast-forward*) e faz `git pull --rebase`, e os lidos se juntam pelo `merge=union`. Recomendo que, com o coord no ar, o time **pare de gravar à mão** (P1).
- **R5 🟢 Trava abandonada por engano.** Só se um único comando git passar de 180 s sem renovar a trava, e o timeout de cada comando é 120 s. Mesmo assim, o `main` fica protegido pelo push sem force; o risco é só de dois processos dividirem a pasta do bare (o índice temporário é por pid).
- **R6 🟢 Autoria dos commits.** É a identidade do git da sessão (ou `bap-coord@bap-coord.invalid`). O remetente verdadeiro está no cabeçalho do recado e no id.

## 11. Plano B (só no desenho, D3)

Entra só se o proxy passar a barrar o push ao `main` (R1), e com nova decisão do Alexandre. **Nenhum código dele está na proposta.** Sem a Action no repositório de recados, gravar no ramo da sessão deixaria os recados presos lá; por isso o coord não tem variável de ramo.

Como seria:
- o coord grava, com o mesmo gravador, no ramo `claude/<sessão>` do repositório de recados;
- uma Action nova no repositório de recados (`integrar-recados.yml` + `.github/scripts/integrar-recados.mjs` + funções puras em `recados-lib.mjs`) integra no `main`:

**A resolver antes de ativar (P4):**
1. **Workflow vindo do ramo.** No `on: push`, o GitHub roda o `.yml` do commit empurrado, e não o do `main`. A mitigação "o script vem do checkout do `main`" não vale: quem empurra o ramo pode trocar o próprio `.yml` (inclusive o `ref:` do checkout). Caminhos: disparar só por `schedule` e `workflow_dispatch`, que sempre usam o `.yml` do ramo padrão; ou um *ruleset* que barre `.github/**` nos ramos `claude/**` [SUPOSIÇÃO: depende do plano do GitHub da conta].
2. **Nome do ramo.** O filtro `claude/[A-Za-z0-9._-]+` da Action não aceita a barra que a validação do coord aceitava (`[A-Za-z0-9._/-]`, sem `..` nem `/` no início ou no fim). As duas regras têm de ser a mesma, de um lado e do outro.
