## 2. Modelo: guardar só as exceções ao perfil

Cada usuário ganha um campo `acesso` em `usuarios.json`:

```json
"maria.x": {"perfil": "vendas", "...": "...",
            "acesso": {"menos": ["vc_planner"], "mais": ["pv_pedidos"]}}
```

- `menos`: rids que o perfil vê e este usuário **não** vê (tirados).
- `mais`: rids que o perfil não vê e este usuário vê (liberados, P1 B).
- Sem o campo (todos os usuários de hoje) = sem exceção = o perfil puro. **Não há migração.**
- Listas ordenadas, sem repetição; um rid nunca fica nas duas; `menos` só guarda rid do perfil e `mais` só rid fora dele (o servidor normaliza ao gravar).

**Por que exceções, e não a lista fechada de faróis por usuário:**
1. **Farol novo segue o perfil sem migração.** A T-0025 v2 (Garantias, Devoluções, NCC, DDR, Campanhas, Expositores) e as próximas acrescentam rids a `render.FAROIS`; com exceções, quem é do perfil já vê. Com a lista fechada, cada farol novo pediria um script para acrescentar o rid em todo usuário do perfil, e um esquecimento deixaria a equipe sem o farol.
2. **Mudança de regra por perfil continua numa linha** (`LEITURA_GERAL`, a D1): chega a todos.
3. **O caso comum fica vazio:** só os personalizados têm o campo, e só eles levam o selo na tela.
4. **Falha segura:** rid desconhecido em `mais` não libera nada (§7).

**Custo aceito:** um usuário restrito passa a ver um farol novo do perfil sem o admin mexer. É o "o perfil dá o padrão" do pedido; vai como P3 (§9).

## 3. Onde é checado: uma função pura

**Módulo novo `web/app/acesso.py`.** Só funções puras, sem I/O; importa `render.FAROIS`, `render.VEEM_PAINEL` e `render.GRUPOS_MENU`.

```python
PAINEL = "vc_painel"                       # = main.PAINEL_RID; o Painel Executivo entra na lista (P2 A)

def rids_da_lista() -> tuple[str, ...]           # Painel + os rids de FAROIS, na ordem do menu (GRUPOS_MENU)
def perfil_ve(perfil: str, rid: str) -> bool     # o padrão: rid conhecido e perfil na tupla (VEEM_PAINEL para o Painel)
def pode_ver(usuario: dict, rid: str) -> bool    # perfil + exceções (abaixo)
def liberado(usuario: dict, rid: str) -> bool    # pode_ver e não perfil_ve: o farol veio por "mais" (a tela marca)
def farois_do_usuario(usuario: dict) -> list[tuple[str, str]]   # substitui farois_do_perfil no menu e na página inicial
def excecoes(perfil: str, marcados: set[str]) -> dict           # do formulário (caixas marcadas) para {"menos", "mais"}
def mudancas(antes: dict, depois: dict) -> list[tuple[str, str]]   # [(rid, "+"|"-")] para o registro
```

```python
def pode_ver(usuario, rid):
    if rid not in rids_da_lista():          # rid desconhecido (ou que saiu do FAROIS): nunca
        return False
    a = usuario.get("acesso") or {}
    if rid in a.get("menos", ()):
        return False
    return perfil_ve(usuario["perfil"], rid) or rid in a.get("mais", ())
```

- `usuario` é o dicionário de `Usuarios.obter`, que passa a devolver também `acesso` (cópia).
- `excecoes(perfil, marcados)`: `menos = padrão − marcados`; `mais = marcados − padrão`. Rid desconhecido no formulário: `ValueError` → 400.
- **Fonte única:** `render.farois_do_perfil(perfil)` continua só como o padrão (é o que `perfil_ve` usa); nenhuma rota pergunta `perfil in FAROIS[rid][1]` de novo.

**Pontos que passam a usar `pode_ver(u, rid)`** (no `main.py`, mais o `render`):

| # | Ponto | Hoje | Depois |

## 4. Ordem das checagens

Em toda rota de farol, nesta ordem (a primeira que falha decide):
1. **Sessão:** `usuario(request)` (logado, ativo, sessão válida; troca de senha pendente → `/senha`). Sem mudança.
2. **A tela do farol:** `acesso.pode_ver(u, rid)`; falso → 403 (a mesma página "Você não tem acesso a esta página.").
3. **Os cortes de dado, pelo perfil, por cima:** `ve_aba` (RN-GER-014), `RESTRITAS` (RN-GER-015), meta RH (RN-GER-001), `EDITA` (RN-GER-012), `cobranca.VE_TABELAS`/`COBRA` (RN-POS-004), `PODEM_PEDIR`, a correção só do admin. **Continuam lendo `u["perfil"]`**, nunca as exceções (na P4 A; a P4 B muda só o `ve_aba`, §9).
4. **Sanitização do conteúdo:** `COLUNAS_FORA`, `coluna_proibida`, RN-GER-011 (telefone e documento nunca no site). Não depende de perfil nem de usuário.

## 5. O que o perfil "de fora" vê num farol liberado, farol a farol

**Como ler:** "de fora" = um perfil que não vê o farol pelo padrão e o ganhou por `mais`. Com a ordem do §4 (P4 A), ele passa no passo 2 e cai fora de todas as listas brancas do passo 3. O pacote é o mesmo para todos (`ind.farol(rid)`, não é montado por perfil); o que muda é só o que a web desenha.

**Legenda:** R = só o Resumo (cartões, gráficos e as tabelas do painel do PC, que já saem sem coluna de cliente, `render.coluna_proibida`), o mesmo que o diretor vê hoje · 403 = negado · — = não se aplica.

## 6. Dado que muda com a ampliação

**Resposta curta:** nenhum farol mostra a um usuário "de fora" uma coluna ou uma aba que o perfil dele não poderia ver por regra. Não há pacote montado por perfil, e todos os cortes de dado são listas brancas de perfil: quem vem de fora cai **fora** de cada uma (vê menos, nunca mais). O `RESTRITAS` (TOTAL A PAGAR) também é lista branca, então a ampliação não o abre (RN-GER-015 preservada). Telefone e documento nunca chegam ao site (RN-GER-011).

**O que o po precisa levar ao Alexandre antes do código (vira a P4, §9):**
1. **Liberar = só o Resumo, nos faróis com tabela.** Pela leitura do po ("as restrições de dado continuam pelo perfil"), o `VE_TABELAS` é restrição de dado (é a D1, "quem vê as tabelas"). Então um vendedor com o Farol de Pedidos liberado vê **o mesmo que o diretor**: cartões e gráficos; as abas Pedidos e Solicitação dão 403, e o Exportar também. Se o Alexandre esperava as abas (as tabelas com cliente), é a P4 B, e aí sim entra dado novo para aquele usuário: **nome e código de cliente**, linha a linha, nas tabelas do farol liberado (sem telefone e sem documento).
2. **O Painel Executivo liberado vem inteiro.** Não há corte por perfil dentro do Painel: um vendedor ou um pré-venda com o Painel liberado vê o mesmo que o gerente, inclusive o **Markup**, o **Preço** e a **Inadimplência** da BAP inteira. É a tela liberada, como decidido; fica registrado aqui por ser o número do Diretor.
3. **Os faróis do Analista Comercial liberados** (Saldo, Markup, Preço, Divergências) mostram no Resumo o desconto comercial, o markup e o preço agregados. Mesmo caso do item 2: é a tela, sem dado de cliente.
4. **A parcial de Pedidos e de Visita segue a tela.** Hoje ela é de quem vê o farol (`PERFIS_PARCIAL = FAROIS[rid][1]`); o liberado passa a ver a imagem que o PC gera [SUPOSIÇÃO: a parcial de Pedidos e a de Visita são por vendedor, sem cliente e sem meta RH; a de Entregas, que lista cliente, continua só de quem vê a tabela]. Alternativa: a parcial fica só pelo perfil (o liberado vê a tela sem o botão da parcial).

Os itens 2 a 4 não pedem decisão nova (são a tela, como no P1 B); o item 1 pede (P4).

## 7. Casos de borda

| Caso | Comportamento |
|---|---|
| Usuário sem o campo `acesso` (todos os de hoje) | Segue o perfil. Sem migração. |
| Admin mexe no próprio acesso | Pode tirar faróis de si. "Usuários" e "Trocar senha" **não estão na lista**: o admin não tem como tirar de si mesmo a tela Usuários (estrutural, não uma checagem). As travas de hoje continuam: ninguém desativa a si mesmo; não se desativa o último admin ativo. |
| Admin restringe outro admin | Pode. A tela Usuários segue com ele. |
| Nenhum farol marcado | O servidor recusa (400): "Para tirar todo o acesso, desative o usuário." Exceção: perfil sem farol no site e sem nada liberado (o `trade` até a T-0025 v2) grava normalmente. |
| Usuário desativado | Exceções mantidas; não entra, como hoje (`autenticar` → "invalido"). O admin pode ajustar o acesso antes de reativar. |
| **Rid que deixou de existir** (saiu de `render.FAROIS` ou foi renomeado) | `pode_ver` → falso sempre (o rid não está em `rids_da_lista()`), em `mais` ou não. A tela não mostra. A entrada fica **inerte e guardada**: o formulário só reescreve os rids conhecidos e preserva os desconhecidos. Se o rid voltar, a exceção volta junto. Rid renomeado = rid novo, que segue o perfil; o PR que renomear um rid leva a migração de `menos`/`mais` (item do checklist do modulo-web). |
| Rid em `mais` que passou a ser do perfil (ex.: a regra do perfil mudou) | Sem efeito (o perfil já vê); na próxima gravação, o servidor tira o rid de `mais` sem linha no registro (não muda o que a pessoa vê). |
| Rid em `menos` que o perfil deixou de ver | Inerte (o perfil já não vê); sai na próxima gravação, sem linha no registro. |
| Farol novo no perfil | Chega marcado para todos do perfil, inclusive os personalizados (P3 A). |
| Troca de perfil | **Não existe hoje** e fica fora da T-0050. Quando entrar: as exceções são recalculadas para manter os mesmos faróis vistos ou zeradas (decisão daquela tarefa), com as linhas no registro. |
| Sessão aberta quando o acesso muda | Vale no próximo clique (toda rota lê `usuarios.obter`). Não derruba a sessão. |
| Dois admins salvando ao mesmo tempo | `Usuarios.trava`: o último grava; o registro mostra os dois, na ordem. |

## 8. Tela Usuários e registro

### 8.1 Tela (para o designer-ux simular)
- **Na linha de cada usuário:** um `<details>` novo, "Faróis", ao lado de "Trocar senha", com **duas partes separadas** (pedido do Alexandre no P1 B):
  - **"Do perfil <Perfil>"**: os faróis do padrão, agrupados como o menu (Diretoria · Pré-venda · Pós-venda · Vendas · Analista Comercial · Trade), **marcados**; desmarcar = tirar.
  - **"Liberar além do perfil"**: os outros faróis, **desmarcados**; marcar = liberar. Ao lado de cada um, o que a pessoa vai ver (na P4 A: "só o Resumo"; no Painel: "o Painel inteiro").
  - Botão "Salvar acesso" (`acao=acesso`, `farol=<rid>` repetido, mais `lista=1` para distinguir "nada marcado" de formulário velho).
- **Selos na linha:** "n a menos" e "n liberados" quando houver; sem selo = segue o perfil.
- **No menu do usuário:** o farol liberado aparece no grupo dele, como os outros [SUPOSIÇÃO: sem marca visual para o próprio usuário; o designer-ux decide].
- **Última mudança:** uma linha discreta no painel, "Alterado em 27/11 06h30 por <admin>", da última linha do registro para aquele usuário.
- **No "Novo usuário":** as mesmas duas partes, logo abaixo do Perfil. Um `static/usuarios.js` pequeno (a CSP de hoje, sem inline) refaz as duas partes quando o perfil muda. Sem JS, aparecem todas as caixas desmarcadas com a frase "Os faróis do perfil entram sempre; marque só os liberados a mais", e o servidor entende as marcadas fora do perfil como `mais` (o `menos` só se ajusta depois, na edição).
- **Fixos, sem caixa:** "Usuários" (admin) e "Trocar senha" (todos).
- **Textos** (rótulos, selos, erros) pelo designer-ux; os nomes dos faróis vêm de `render.NOME_MENU` / `FAROIS` (fonte única).

### 8.2 Registro (só de acréscimo)
- **Arquivo:** `<BAP_WEB_DADOS>/usuarios_acesso.jsonl` (no Render, `/var/data/usuarios_acesso.jsonl`), ao lado do `usuarios.json`. **Sem retenção** (~150 bytes por mudança). Nunca é reescrito nem apagado pela web; fica fora da limpeza dos 90 dias de `acessos/`.
- **Uma linha por farol mudado:**

```json
{"quando": "2026-11-27T06:30:12-04:00", "lote": "c1f3...", "quem": "admin.login", "alvo": "maria.x",
 "perfil": "vendas", "rid": "pv_pedidos", "mudanca": "+", "origem": "liberado", "acao": "editar"}
```

  - `quando`: hora de Manaus com o fuso; `lote`: um id por gravação;
  - `mudanca`: `+` = passou a ver; `-` = deixou de ver;
  - `origem`: `perfil` (o rid é do padrão: `-` tirou, `+` devolveu) ou `liberado` (fora do perfil: `+` liberou, `-` tirou a liberação);
  - `acao`: `criar` ou `editar`.
- **Sem dado de cliente**, sem IP, sem navegador. O login é o identificador que o `acessos/` já guarda [SUPOSIÇÃO: aceito pela regra 6, como no `acessos/`; o revisor-codigo confere]. No log do Render (`stdout`), só "acesso de usuário alterado", sem login.
- **Ordem da gravação**, dentro de `Usuarios.trava`:
  1. acrescenta as linhas no `.jsonl` (`open(..., "a")`, `flush` e `os.fsync`);
  2. grava o `usuarios.json` (`gravar_json`, atômico);
  3. se o 2 falhar: acrescenta `{"lote": ..., "acao": "desfeito"}` (melhor esforço) e a tela mostra 503 "Não foi possível gravar agora.". Se o 1 falhar, nada muda, e a tela mostra o mesmo 503.
- **Sem mudança efetiva:** nenhuma linha.
- **Leitura:** `Usuarios.ultima_mudanca(login)` para a linha "Alterado em ... por ...". Tela de histórico completo: só se o Alexandre pedir.
